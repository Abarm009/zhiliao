# 比赛视频重拍方案

日期：2026-10-08。现有文件：`submission/2026-10-06/video/zhiliao-demo-putonghua.mp4`；本次 ffprobe 实测 82 秒、1280×900、30fps。旧片保留，重拍输出另命名，不直接覆盖。

## 看见的问题

第 50 秒是整屏步骤文字页，用 ACCEPTED→SCHEDULED 等术语讲流程，缺少实际点击与结果。第 74 秒的原生界面被放大裁切，标题和身份占去大部分画面，任务与动作结果看不全。不是单纯换旁白能修好，应在原生 UI 更新后重拍操作。

设计原型可用于排练与选择镜头，**不能冒充原生比赛演示**。若最终原生仍缺真实附件链路，视频明确标出 Web 演示与原生候选两段，前者展示已验证完整业务链路，后者只展示真实跑通的操作和诚实的阻断，不拼成原生全链路。

## 拍摄方法

- 目标视频约 84 秒，具体上限先按比赛当前规则核对。建议画布 1920×1080、30fps，应用保持完整窗口；若素材为 1440×900，等比放入画布并留边，不拉伸裁切。
- 先在 1440×900 内容区检查布局。隐藏开发终端、日志、密钥和无关通知。保留任务标题、当前角色、状态和主动作。
- 鼠标一次指向一个动作，点击后停留 2–3 秒，让观众看到角色、状态和反馈。必要特写保留任务上下文，不把标题放到全屏。
- 文案放字幕，不再用整屏文字页代替关键操作。中文状态优先，英语枚举、文件名和哈希放提交文档。
- 普通话、正式自然的口吻，优先沿用用户已选的第三版 Serena 配音；按新镜头重新对齐时间。旁白清晰压过音乐，音乐淡入淡出，避免与语音争抢。音量最终听测，不仅按数值判定。
- 后半段演示“提交完工 → 待验收 → 退回 → 继续处理 → 再提交 → 独立验收 → 完成”。不能从 COMPLETED 退回重做，也不能让维修者切换显示角色后自验。

## 建议镜头与正式普通话旁白

以下是拍摄脚本，句子中的动作须实际拍到。无法完成的镜头删改并如实说明，不能靠字幕宣称成功。

|时间|画面|旁白|
|---|---|---|
|0–5 秒|完整工作台，任务列表与详情|知了把报修、维修和验收，组织成一条可追踪的协作流程。|
|5–12 秒|报修人输入问题，确认空间与类别|报修人描述问题，确认发生位置，再提交维修任务。|
|12–19 秒|维修身份接单，关联设备；保留同一任务号|维修人员接单后核对设备，问题所在空间和设备信息分别记录。|
|19–26 秒|提议预约，显示完整时间|接下来提出到场时间，让报修人确认安排。|
|26–33 秒|报修人确认，状态更新为已预约|预约确认后，双方都能看到负责人和维修时间。|
|33–41 秒|按约开工，填写真实处理记录|维修人员按约处理，记录检查结果和已经完成的工作。|
|41–49 秒|真实证据上传与校验，展示附件结果|维修证据随任务保留，提交完工前先检查证据是否可用。|
|49–56 秒|提交完工后明确“待验收”|提交完工只是进入待验收，还不等于任务已经完成。|
|56–63 秒|另一身份查看证据，填写退回原因|报修人核对现场与证据。问题没有解决，可以说明原因并退回处理。|
|63–71 秒|补处理和证据，第二轮独立验收，状态完成|维修人员补充处理后再次提交，由独立验收确认完成。|
|71–79 秒|完整原生窗口，真实操作下一步；明确片段来源|原生桌面界面围绕当前任务展开，按角色和阶段呈现下一步。|
|79–84 秒|全窗回到完整记录，简短结尾|每次预约、处理和验收都留下记录，让协作结果可以核对。|

第 41–71 秒只有真实闭环验证通过才采用。若原生上传仍阻断，这段使用实际跑通的 Web 闭环并常驻“Web 业务演示”标签；71–79 秒标“原生候选 · 已验证范围”，只录新建/预约或真实证据阻断。原生仍缺能力时结尾改为：“当前原生候选已接入部分流程，真实附件和完整验收仍在完善。”

## 应补拍的提交截图

1. 完整桌面任务详情：位置、设备、当前角色、下一步一起可见。
2. 预约确认：日期、时段、负责人、确认后的状态。
3. 维修进度与真实附件：明确已就绪或真实阻断原因。
4. 独立验收：由合规另一身份验收，展示轮次与依据。
5. 完成后的完整处理记录：任务号与最终状态可核对。

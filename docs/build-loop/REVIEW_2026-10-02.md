## 1. P0：宣称的能力不成立

### R-P0-1 · 原生 UI 只实例化了声明节点的一半，退回/重置/任务列表/状态行不存在

**现象**：`main.splash` 声明 23 个节点，运行时 `/d` 只返回 23 个总节点，其中 splash 内仅 15 个（2 Label + 13 Button），最后一个节点是"验收"（`Button e 12 793 63 40`）。

**根因**：[main.splash:174](../../app/bundle/main.splash#L174) 根容器是 `SolidView{width: Fill height: Fill flow: Down ...}`，子节点超出 `body`（412×816 布局点）时被**丢弃**，不是裁剪也不是滚动。

**复现**：
```sh
MAKEPAD_REMOTE=8823 runtime/native-build/OctoSense-App-Hub/target/release/card-host \
  --bundle app/bundle --app-data /tmp/x --allow-unsigned --stamp &
curl -sS http://127.0.0.1:8823/d      # W3 23，末节点为 Button e "验收"
curl -sS http://127.0.0.1:8823/snap   # 23 widgets，只有 13 个 Button
```

**影响**：`退回`、`重置演示`、任务列表面板（含"任务列表（N）"）、状态行共 8 个节点在运行中的应用里点不到也看不到。README / app/README / SUBMISSION §12 宣称的"9+ 按钮（…/退回/重置）"与"重启回读任务与最后状态"不可能成立；退回重做链（T21）在原生 UI 无法复现；违反 15 号文档 L6「真实截图无关键裁切」与 10 号文档 §9。

**修改建议**（三选一，按工作量排序）：
1. **拆分容器**：把 4 个角色按钮收进一个横向 `View{flow: Right}`，业务按钮按阶段分组到 2-3 个 `View`，总高度压到 ≤780 点。改动最小，不动交互。
2. **加滚动**：根容器外包一层可滚动视图（需确认所用 OctoScript 版本的 ScrollView 构造名与 `flow: Down` 兼容），保留全部按钮。
3. **分页/状态机**：按任务阶段只渲染当前可用动作（这也是 15 号文档 §2「每个状态只突出当前主体的一个主要动作」的要求），天然不会溢出。

无论选哪种，都需要重新 `hub stamp` + `hub check` + `hub scan` + 重截 3 张图（首屏/操作后/重启后），并替换 `app/bundle/screenshots/01-main.png`。

### R-P0-2 · core 命令的角色校验不按 project 隔离，跨项目可写

**现象**：`u-reporter-2`（只有 prj-B 的 REPORTER）能在 prj-A 建档；`u-manager`（只有 prj-A 的 MANAGER）能在 prj-B 建档。

**根因**：[commands/__init__.py:92-99](../../backend/src/octosense_backend/commands/__init__.py#L92-L99) `_check_actor_role(project_id, actor_id, allowed)` 收了 `project_id` 却不用；[api/__init__.py:63-74](../../backend/src/octosense_backend/api/__init__.py#L63-L74) `_resolve` 的 SQL 是 `WHERE user_id=?`，无 project 过滤；且 `if "MANAGER" in roles: return` 是全局放行。对照 [extended.py:132-143](../../backend/src/octosense_backend/extended.py#L132-L143) 的 `_check_role` 是**按 project** 查的（`list_tasks` 跨项目正确返回 403）——两套标准并存。

**复现**：
```sh
curl -sS -X POST localhost:8821/api/octosense/v1/tasks \
  -H 'X-Actor-Id: u-reporter-2' -H 'Content-Type: application/json' \
  -d '{"idempotency_key":"k","project_id":"prj-A","problem_text":"x","contact_name":"y"}'
# → 201（应 403）
```

**影响面**：create_draft / confirm_draft / accept_task / assign_task / propose_appointment / start_progress / submit_completion / accept_completion / reject_completion / cancel 共 10 个命令；T03/T05/T18 因此不成立。

**修改建议**：把 `actor_resolver` 的签名改成 `resolve(project_id, actor_id) -> set[str]`，SQL 加 `AND project_id=?`；`_check_actor_role` 改为先按 project 取角色，为空抛 `PermissionDenied`，再判 `roles & allowed`；MANAGER 代行限制在**同一 project** 内。同步改 [conftest.py:39-50](../../backend/tests/octosense_backend/conftest.py#L39-L50) 的同名 fixture。补一条测试：`test_cross_project_accept_rejected`。

### R-P0-4 · 「同 key 不同内容返回 409」未实现，幂等冲突是死代码

**现象**：同一 idempotency_key 配不同 payload，第二次返回 `idempotent_replay: true` + HTTP 201。

**根因**：[commands/__init__.py:101-112](../../backend/src/octosense_backend/commands/__init__.py#L101-L112) `_check_idempotency` 只要上一次 `result='OK'` 就回放，**不比较 payload**。`IdempotencyConflict` 只在"上一次 result=ERROR"时抛出，而 `grep '"ERROR"' backend/src/octosense_backend/` 零命中——没有任何代码写过 `result='ERROR'`，所以该类错误与 docstring 宣称的「失败也记 action（result=ERROR）保证审计」都不成立。

**复现**：
```sh
# 两次仅 problem_text/contact_name 不同，key 相同
# 1st → 201；2nd → 201 {"idempotent_replay":true,...}   （应 409 IDEMPOTENCY_CONFLICT）
```

**修改建议**：`repair_actions` 增列 `payload_hash TEXT`（需迁移已有库：`ALTER TABLE ... ADD COLUMN`，旧行置 NULL 视为不比较）；`_record_action` 写入 `sha256(canonical json of 业务参数)`；`_check_idempotency` 命中时若 hash 不相等抛 `IdempotencyConflict`。同时把失败动作真正写成 `result='ERROR'`（在命令层统一 try/except 记录），让审计与 409 分支都活过来。补测试：`test_idempotency_same_key_different_payload_409`。

### R-P0-5 · demo-web 无法确认预约，web 路径在 SCHEDULED 死锁

**现象**：报修人在 SCHEDULED 状态下唯一可用动作是"取消任务"，没有"确认当前预约"。

**根因**：[workbench.html:192-207](../../app/demo-web/static/workbench.html#L192-L207)：
```js
const confAppt = appts.find(a => a.status === 'CONFIRMED');   // 找的是 CONFIRMED
if (role === 'REPORTER' && status === 'SCHEDULED' && isReporter && confAppt) { ... }
```
条件循环：只有已存在 CONFIRMED 预约才显示确认按钮，而首次确认永远不可能发生。

**复现**（ego-browser 真点击）：reporter 建档 → 确认 → tech 接单 → 绑定 → tech 提议预约 → reporter 看到 `actions: ['取消任务']`；manager 看到 `['改派给另一技工','取消任务']`。

**影响**：浏览器里没有任何入口把 PROPOSED 变 CONFIRMED；`start_progress` 有 CONFIRMED 守卫 → 无法开工 → 无法记录处置/上传证据/完工/验收。**web 端无法到达 COMPLETED**。违反 U04 与 T10/T12 的"报修人确认预约"。

**修改建议**：把 `confAppt` 改成 `appts.find(a => a.status === 'PROPOSED')`，按钮文案改为「确认当前提议（→ CONFIRMED）」；同时把 PROPOSED 与 CONFIRMED 在预约面板里分开展示（U04）。改完后用 ego-browser 复跑完整三角色链直到 COMPLETED，并补一条自动化回归（`page.click` 序列 + 断言最终 status=COMPLETED）。

### R-P0-6 · 无任何身份/授权机制，T29 的 grant 生命周期不存在

**现象**：bundle 只声明 `capabilities: ["storage"]`，没有 grant 申请/关闭/退出/到期路径；后端身份只有一个 demo header `X-Actor-Id`，无会话、无 token、无撤销。

## 2. P1：功能缺陷

### R-P1-1 · 原生任务不落盘，重启后任务丢失并产生重复 id

**现象**：跑完 9 步后 `state.json` 只有 `{"actor","page","selectedIdx","status"}`；kill + restart 后 `TASKS=[]`，点"接单"是 **silent no-op**（events.jsonl 一字不变，无任何用户反馈）；再点"新建草稿"又生成 `tsk-0`，events.jsonl 出现两条 `create_draft` 指向同一 task_id。

**根因**：[main.splash:23](../../app/bundle/main.splash#L23) `save()` 只写 STATE；[main.splash:24-33](../../app/bundle/main.splash#L24-L33) `load()` 不回填 TASKS；[main.splash:47](../../app/bundle/main.splash#L47) id 用 `TASKS.len()` 生成。

**复现**：
```sh
# 点击 9 步 → 读 /tmp/octo-native/octosense-repair/{state.json,events.jsonl}
# kill → 同 app-data 重启 → 再点"接单" → events.jsonl 无变化；点"新建草稿" → 出现第二个 tsk-0
```

**修改建议**：`save()` 增写 `tasks.json`（TASKS 全量，含 id/status/assignee/asset/events）；`load()` 回填并校验 `selectedIdx` 越界时置 0；id 改用 `uuid` 或持久化计数器；`events.jsonl` 改名为 `.json` 或真正按行写（当前 `EVENT_LOG.to_json()` 写的是 JSON 数组）。顺带修 [main.splash:37-43](../../app/bundle/main.splash#L37-L43)：`resetDemo()` 要同时清磁盘 events。

## 2. 当前问题与修改建议

### R2-01 [P1] 原生实际提交仍失败，原始包也仍不能准入

位置：`app/bundle/manifest.json`；`app/bundle/main.splash:303–315` 及动作调用链。

原包实际 digest 为 `e2426a4fb170319a8174f873217db79cabe0a068bf022304ef52eaa04c1a342b`，manifest 声明仍为 `c066a517776438e1e4593f3f106f6a5ba24c5eb6668be7e18a2bded4bdbbaf82`。副本打戳后确实 admitted、view=true，并能点击创建草稿落盘；但点击“提交报修（→ OPEN）”后，tasks.json 仍 DRAFT、version=0，actions 中没有提交回执。切换技工再点击接单同样没有进入 ACCEPTED。宿主日志包含 `no getter for field id on type nil` 和 `call target is not a function (got nil)`。

**影响：** 原生业务主链未打通，不能归结为仅按钮可见性问题。宿主日志行号可能含包装偏移，本轮未把它当成精确根因定位。

**建议：** 在固定宿主上定位真实点击后的函数绑定/作用域与空值问题，以“任务变 OPEN + 新回执 + 新事件”验收提交，再完成接单到验收及重启恢复；只看 eval/view=true 或进程退出 0 不够。最终对实际交付目录生成摘要并重新执行 Hub 检查。

### R2-02 [P1] 原生“上传证据”仍凭空写 READY 元数据

位置：`app/bundle/main.splash:558–574,595–608`。

静态确认：addEvidence 直接写入 `bytes:32`、`sha:id+"-sha"`、`ready:true`，没有文件选择、文件内容写入或实际摘要计算；完工守卫只检查 readyCount。界面却提示“宿主隔离存储内可回读”。Python 侧附件完整性修复没有覆盖此原生实现。

**建议：** 接通实际文件获取、隔离存储、真实字节数/摘要和授权下载回读，成功后才允许 READY；提交完工时重新检查内容完整性。若固定宿主无法完成，明确记录未接通，不能用占位元数据通过业务验收。本轮没有声称原生已经走到完工：此项是代码直接证据。

### R2-03 [P1] Web 新建表单缺空间，新增草稿无法提交

位置：`app/demo-web/static/workbench.html:344–356`；`backend/src/octosense_backend/commands/__init__.py:337–345`。

Web createDraft 的请求没有 space_id，也没有对应空间选择控件。按当前表单的实际载荷调用：创建 201，随后 confirm 返回 **422 SPACE_REQUIRED**，任务保留 DRAFT。现有表单也没有给该草稿补空间的完整入口。

**建议：** 增加按项目加载的服务空间和任务类别选择，创建时传入有效值；为已有草稿提供带权限/版本控制的补充修改入口。新增真正从 Web 表单创建到三角色完成的浏览器用例，不能只在 API 测试里手工补 space_id。

### R2-04 [P1] 联系人虽在 task 脱敏，仍从事件快照泄露

位置：`backend/src/octosense_backend/api/__init__.py:442–447,485,647–652`。

未接单技工查看技能匹配 OPEN 任务，task.contact_info 为 null，但 detail.events 的 before/after 仍包含 `private-contact`；同一主体 GET /events 也返回该值。_event_out 直接反序列化原始快照，没有调用字段授权策略。SSE 也复用该函数，存在同源风险，但本轮没有另行读取 SSE 流作实测。

**建议：** 为详情、事件轮询、SSE 和历史建议使用同一主体感知的事件输出策略；避免把完整数据库任务行作为无差别对外事件载荷。补“主字段与所有嵌套快照均不含联系人”的断言。

### R2-05 [P1] 撤销项目权限后仍能写处置记录，并回放创建回执

位置：`backend/src/octosense_backend/extended.py:495–511`；`commands/__init__.py:239–250`。

两个实测反例：

- 原承接技工被移出 A 项目、保留 B 项目身份后，读取 A 任务为 404，但 POST /progress 仍 **200**，任务版本从 7 变 8。record_progress 仅检查 assignee_id，没有校验当前项目授权。
- 原报修人被移出 A 项目后，详情为 404，但使用原 create_draft 幂等键重试仍 **201**，回放原任务 ID、项目和结果。_run 的回放授权仅在请求 task_id 非空时执行；创建请求恰好为空。

**建议：** 在统一命令边界对首次执行及回放都校验当前身份、项目成员关系和对象权限；创建回放应从已存回执取得真实 task_id 后授权。不要仅依赖各 body 分散补守卫。新增撤权后的所有写操作与回放矩阵，确认失败时版本、事件、回执不产生业务变化。

### R2-06 [P1] 开工 A 错把其他任务 B 的预约提议作废

位置：`backend/src/octosense_backend/commands/__init__.py:526–530`。

SQL 使用 `WHERE task_id<>? AND status='PROPOSED' AND technician_id=?`。实测 A 有已确认预约及另一未确认改约，B 有不重叠提议；启动 A 后，**A 自己的新提议仍 PROPOSED，B 的提议反而 SUPERSEDED**。

**建议：** 将失效范围限定为当前任务的未确认提议，并保证对应事件/版本规则一致；对其他任务的冲突应使用预约冲突规则，不应全量作废。回归同时断言“本任务提议失效、其他任务非冲突提议保留”。

### R2-07 [P1] 提醒没有随预约和任务状态失效，完成后仍催办

位置：`backend/src/octosense_backend/jobs.py:38–48,72–117` 以及 start/accept-finish/reject-finish 状态转换。

实测：改约时旧技工提醒和超时提醒被取消，但漏掉 `APPOINTMENT_UPCOMING_REPORTER`，在旧时间仍向报修人发提醒。另一任务已 COMPLETED，继续运行到期作业仍生成 **4 条**通知，包括“预约将开始”“预约已超时，需要重新预约”“待你验收”。执行器没有依据当前任务/预约状态重新确认作业是否有效。

另有静态缺口：验收提醒去重键只有 task_id+reporter_id，不含 completion_id/轮次，无法正确表达退回后的新一轮提醒；此分支本轮未另做动态复现。

**建议：** 在改约、开工、取消、验收、退回时事务内取消相关作业；执行前再次核对任务状态、有效预约和完工轮次。按预约/完工轮次生成幂等键，补旧预约、已完成、重做轮次和重启后的提醒测试。

### R2-08 [P1] 任意已注册用户可触发全局作业并读取其他项目任务元数据

位置：`backend/src/octosense_backend/api/__init__.py:614–625`。

POST /jobs/tick 只验证用户已注册，随后执行全库到期作业，并返回全库前 50 个 PENDING 作业。实测 B 项目报修人查看 A 任务为 404，但 tick 为 **200**，响应包含 A 任务的 3 个 job（任务 ID、预约 ID、时间）。

**建议：** 将全局调度入口限制为内部调度器/明确管理权限；面向用户的作业查询按项目和对象授权过滤。不可把“已注册”当作全局任务控制权限。

### R2-09 [P1] 设备绑定仍放行报修人提交后改设备

位置：`backend/src/octosense_backend/extended.py:186–205`；基线 `docs/implementation/01_REQUIREMENTS.md:45,93`。

基线明确 OPEN 仅经理绑定，ACCEPTED/SCHEDULED 由承接技工或经理处理，报修人仅 DRAFT 可选。当前 else 分支允许原报修人继续绑定。实测 OPEN 任务由原报修人绑定返回 **200**，asset_id 实际变为 as-a-1。修复者探针 Ctx.accepted 也使用报修人在 ACCEPTED 阶段绑定作为前置步骤，掩盖了矩阵偏差。

**建议：** 按状态显式定义主体权限，保留已修复的 IN_PROGRESS 经理+理由规则；同时修正测试铺垫，使用合法主体，不要通过修改业务基线迎合当前实现。

### R2-10 [P2] HTTP 作业入口丢失应用注入时钟

位置：`backend/src/octosense_backend/api/__init__.py:618,706–709`。

make_app 注入时钟，但 jobs_tick 经 _run_due_jobs(db) 最终调用 run_due_jobs(db)，未传 clock。实测将应用时间推进到提醒到期，HTTP tick 产生 **0** 通知；随后同库传入正确时钟执行，产生 **2** 条通知。预约命令与作业看到不同的“当前时间”。

**建议：** 调度入口共用应用时钟依赖，在 HTTP 路径验证到期行为；不能只测直接调用 jobs 函数的可注入时钟。

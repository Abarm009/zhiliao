## 三、逐项修复与可判定验收标准

### R2-01｜原生提交失败与原始包准入失败（P1）

**已发现问题：** 原包 digest 不匹配；副本打戳后可创建 DRAFT，但点击提交不变 OPEN，宿主有 nil getter / call target nil。不是仅按钮显示问题。

**修改要求：** 在固定宿主上定位函数绑定、作用域、空值及动作分发问题。让可用动作由当前角色/状态决定，执行层仍强制授权。修复实际应用脚本，不以修改宿主、跳过守卫或直接改 tasks.json 代替点击。最终为实际交付目录重新生成摘要。

**验收标准：**

- 对最终 `app/bundle` 本体运行项目规定的 Hub 检查并通过；如果当前开发流程允许 unsigned，明确记录 unsigned，不能宣称已签名或已上架。
- 固定宿主成功加载；完整点击过程中没有未处理解析/求值异常。不能只搜索首次 eval 的日志。
- 在原生界面真实完成：创建 DRAFT → 提交 OPEN → 合法技工接单 ACCEPTED → 合法绑定设备 → 提议预约 → 报修人确认 SCHEDULED → 预约窗口内开工 IN_PROGRESS → 记录处置/真实证据 → 提交 AWAITING_ACCEPTANCE → 有理由退回 IN_PROGRESS → 再次完工 → 合法验收 COMPLETED。
- 每次写操作回读实际状态、版本、操作者、业务事件和回执；失败操作没有部分写入。通过界面输入真实字段，不能用固定演示文本替代业务输入。
- 关闭本轮宿主并用相同 app-data 重开：任务 ID、最终状态、事件历史、两轮完工和证据引用仍完整；对 events.jsonl 验证多条记录恢复，不只单条。
- 非法角色/非法阶段动作不可成功执行；按钮可见性符合现有 UI 基线。宿主限制若仍存在，独立记录，不能把“按钮能点击但无响应”作为权限实现。

### R2-02｜原生证据是虚构 READY 元数据（P1）

**已发现问题：** addEvidence 写死 bytes=32、伪造 sha，未存真实文件；完工只计 readyCount。

**修改要求：** 接入宿主实际允许的文件获取与隔离存储，计算真实长度和 SHA-256，保存成功后才标 READY；读回和完工检查真实内容。保留授权、数量/大小/类型等已有约束。不用生成空壳文件或演示内容冒充用户上传。

**验收标准：**

- 从原生用户入口添加至少两份内容不同的真实测试文件；原始内容与下载/读回内容逐字节相等，长度、摘要一致且跨重启可回读。
- 未授权用户不能上传、读取或隔离不属于其权限范围的证据。
- 上传失败或中断不会产生可用于完工的 READY 记录。对缺失、损坏、隔离文件分别测试，完工必须被拒绝，任务版本、完工记录与成功回执没有半写；独立失败审计可以按设计追加。
- 恢复合法文件或重新上传后可以重新提交；两轮完工及证据归属按基线保留。
- 如固定宿主确实不支持所需能力，给最小能力探针和日志，保持该项 BLOCKED、相关完工验收未通过；禁止回退成假元数据。

### R2-03｜Web 表单缺空间导致无法提交（P1）

**已发现问题：** createDraft 没传 space_id，创建成功后 confirm 返回 SPACE_REQUIRED，缺乏补齐入口。

**修改要求：** 提供按当前项目加载的空间、任务类别及必要联系信息输入；提供本人 DRAFT 的补充编辑，接入统一权限、版本、幂等和事件。项目变更必须使不再合法的空间/设备选择失效，不自动猜定。

**验收标准：**

- 从真实 Web 表单创建、提交，数据库空间/类别与选择一致，DRAFT 正常进入 OPEN；不允许测试通过绕开页面、后台补字段来伪装浏览器成功。
- 历史缺空间草稿可以合法补齐后提交；未补齐时明确提示并保持 DRAFT。
- 跨项目空间、无权限修改、提交后直接修改草稿字段、旧版本覆盖均按契约拒绝，无业务副作用；合法原请求重试不重复写入。
- 切换报修人、技工、经理完成浏览器主链，至少验证技工发现 OPEN、接单、正确设备主体、预约确认、证据、完工和验收；界面状态与后端回读一致。记录浏览器和 API 证据各自范围。

### R2-04｜事件快照绕过联系人脱敏（P1）

**已发现问题：** task.contact_info=null，但详情 events 和 GET /events 仍含原联系人；SSE 复用同一原始序列化函数。

**验收标准：**

- 使用唯一测试联系人标记：未接单但能看 OPEN 的技工，读取上述所有实际存在的入口时，响应任意嵌套字段及 SSE 帧中均不能出现该标记。
- 合法可看联系信息的主体正常读取，其他项目/无关用户不能通过事件推知无权任务内容。
- 覆盖接单前后、撤销项目权限、历史事件重放；长连接发送新帧前遵循当前授权，撤权后不继续泄露。

### R2-05｜撤权后仍能写入与回放（P1）

**已发现问题：** 从项目移除技工后 detail=404 但 progress=200；移除报修人后旧 create 幂等键仍返回原创建结果。

**修改要求：** 在统一任务命令边界校验当前身份、项目关系和对象权限，涵盖首次执行与幂等回放；创建回放从存储回执解析真实对象。不能只修 progress 单个方法。对现有写入口、旧 runner/工具调用路径作清单检查。

**验收标准：**

- 用户保留 B 项目身份、被移除 A 项目后：读取 A 任务、全部相关写操作和旧请求回放按信息隐藏策略返回拒绝，不泄露原任务数据。
- 覆盖新幂等键、旧幂等键、创建回放、处置、绑定、预约、证据、收藏、建议、完工、验收等已实现命令；分别测试项目移除和操作角色撤销。
- 拒绝后任务/预约/附件/业务事件/成功回执不变；失败审计可以单独追加，但不得对无权主体泄露内容。
- 合法、仍有权主体的原请求重试保留相同 action_id 和原业务结果，不产生第二次副作用；同 key 不同请求按现有契约冲突。不要因为任务已经推进到新状态而使合法幂等重试再次执行或错误失败。
- HTTP 和领域/工具入口均被覆盖，不能仅靠页面隐藏或单个路由守卫。

### R2-06｜开工错误作废别的任务提议（P1）

**已发现问题：** start_progress 的 task_id<>? 作废其他任务，保留本任务未确认改约。

**修改要求：** 开工事务仅失效当前任务不再有效的 PROPOSED 提议；其他任务沿用预约冲突规则，不全量作废。同步保持事件、版本和提醒关系一致。

**验收标准：**

- A 已确认预约，A 另有未确认改约，B 有同技工且不重叠提议。A 开工后：A 未确认提议失效；B 仍 PROPOSED，B 版本、事件及作业不被误改。
- A 失效提议不能再确认；B 在自身规则满足时仍可确认。
- 保留跨任务/跨项目同技工真正时间冲突检查；开始时间窗口守卫不被削弱。
- 重试开工不重复失效、不重复事件；失败时不会留下部分预约状态变更。

### R2-07｜过期提醒未取消与完工轮次去重错误（P1）

**已发现问题：** 改约漏取消报修人提醒；COMPLETED 后仍发预约/超时/验收提醒；验收提醒键无完工轮次。

**修改要求：** 在预约/任务生命周期事务中取消失效作业，执行器发送前再验证任务、预约、接收人权限及 completion 轮次。按预约/完工轮次建立去重；采用本地持久化调度及站内通知，不引入真实对外发送。

**验收标准：**

- 改约后旧预约所有提醒（包括报修人）均不会发，新预约按配置到期触发且各一次。
- 已开工不再发“未开工超时”，已完成/取消不再发预约或待验收催办；已创建的历史通知是否保留按现有产品规则处理，不要求删除历史。
- 首轮完工退回后旧验收提醒失效；第二轮完工生成以第二轮为依据的新提醒，按新提交时间计时；首次提醒已执行与未执行两种情况都覆盖。
- 合法待验收超时只提醒，不自动验收、开工或完工。
- 重复 tick、重启后补执行及并发 tick 不产生重复通知；同时发生的取消/改约与触发具有明确事务顺序，不能发送已失效作业。
- 数据持久化及自动调度入口分别验收：若只有手工 tick，则只能宣称手工执行通过，不能把自动提醒标 PASS。

### R2-08｜全局 jobs/tick 越权（P1）

**已发现问题：** 任意注册用户可执行全库作业，读到其他项目任务 ID/预约时间。

**修改要求：** 全局执行优先收敛至应用内部调度器；普通用户 HTTP 不得借注册身份触发全局处理。如果保留管理接口，必须有明确内部/管理授权，不把任意项目 MANAGER 自动提升为全局管理员。用户作业查询执行对象授权。

**验收标准：**

- A/B 项目都有作业，B 普通用户调用全局执行入口被拒绝或该公开入口已移除；A 作业状态、通知不因该请求改变，响应不含 A 标识/时间/内容。
- 无关项目经理同样不能获得全局权限；匿名、伪造/未注册身份按现有契约拒绝。
- 合法内部调度仍可运行，覆盖全部应执行作业，且不会依赖前端伪造角色字段。
- 用户可见作业列表仅返回其当前有权访问的内容。更新调用方和测试，不留下绕过旧路由。

### R2-09｜设备绑定阶段权限错误及测试基线错误（P1）

**已发现问题：** 原报修人在 OPEN/ACCEPTED 等阶段仍能绑定；修复者 Ctx.accepted 使用该错误操作作为成功铺垫。

**修改要求：** 以业务基线实现如下矩阵；原始报修关系本身不能提升提交后的权限。多角色主体可凭其实际具备的经理/承接技工资格操作，不因它同时是报修人而机械禁止。

| 阶段 | 允许绑定/更正设备的主体 |
|---|---|
| DRAFT | 原报修人，且仍有本项目访问权 |
| OPEN | 本项目经理 |
| ACCEPTED / SCHEDULED | 当前承接技工或本项目经理 |
| IN_PROGRESS | 本项目经理，理由必填，记录旧值/新值 |
| AWAITING_ACCEPTANCE / COMPLETED / CANCELLED | 不直接更改；待验收需按合法退回流程处理 |

**验收标准：**

- 参数化覆盖上述每个阶段的允许/拒绝主体、无关同项目用户、跨项目用户和多角色用户；绑定、更正、解绑共同遵守适用的基线规则，不通过另一个入口绕过。
- OPEN 报修人原反例拒绝且 asset/version/event 不变；合法经理操作通过。
- 服务关系、项目、归档状态、技能、版本和 IN_PROGRESS 理由守卫继续有效；经理换绑有完整旧值/新值/原因审计。
- 修正全部测试 helper、脚本和 Web 操作入口，用合法主体完成铺垫；不得改业务基线为错误实现背书。修正测试要说明其旧期望为何违反基线，不能删除断言换绿。

### R2-10｜作业入口未传应用时钟（P2）

**已发现问题：** 命令使用注入时钟，HTTP tick 却使用真实系统时间，造成同一次业务判断不一致。

**修改要求：** 命令、作业登记、实际调度入口及执行器共用应用时钟；客户端不能指定服务端当前时间。若 R2-08 移除公共 tick，验证替代的真实内部入口，不为测试重新暴露不安全接口。

**验收标准：**

- 注入与系统时间明显不同的服务端时钟：到期前 0 条，到期后恰好预期数量，重复执行不增加；同时验证预约和验收提醒。
- 至少经应用实际调度入口验证一遍，不只直接调用 run_due_jobs 的单测；保留 HTTP 入口时使用合法授权测试。
- 默认无注入时使用真实服务端时间；HTTP 载荷或查询参数不能伪造 now 绕过时间守卫。

## 四、执行顺序与验证纪律

先保留现场、复现缺陷，再修复。建议先处理 R2-01/03 的真实入口，再集中 R2-04/05/08/09 权限，再处理 R2-06/07/10 时间与作业，完成 R2-02 原生附件并跑全链。可据依赖调整，不必请求确认。

1. 将独立反例转为版本库内永久回归测试，前置步骤必须断言成功并回读。注意 `independent_probe.py` 原本记录缺陷现象，不是可直接拿退出 0 当“修好”的门禁；需反转为正确结果断言。复用旧 helper 时先修正 R2-09 的非法设备绑定铺垫，不能让测试卡在铺垫后被当成权限拒绝成功。

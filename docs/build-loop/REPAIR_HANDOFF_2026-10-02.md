## 4. 必修业务边界

### 4.1 统一权限、读取范围和身份

- 服务端按当前主体+项目角色+任务关系+技能+阶段判断；未知主体/跨项目均拒绝，不允许全局 MANAGER 自动越权。
- 报修人只管理自己任务；技工看本项目技能匹配 OPEN 和自己承接任务；经理看授权项目。接单前联系方式按基线脱敏。
- list/detail/events/SSE/history-advice/assets/evidence/pins 等采用一致的可见性规则，客户端 role 参数只能缩小范围，不能扩大。历史建议的 asset_id 不能用于跨项目读取。
- 技工只能代表自己接单/开工/记进度/报完工；经理不是承接者不能伪装技工。分配/改派目标必须是同项目有效技工且技能匹配。
- 预约确认/拒绝仅本任务报修人，P0 经理不代确认。验收/退回仅原报修人或同项目经理，经理理由必填，当前承接者即使多角色也不可自验。
- 报修人仅能取消自己的 DRAFT/OPEN；经理取消范围按原矩阵，终态不能再改变任务事实。
- 默认入口不信任任意 X-Actor-Id。实现可验证的本地独立主体会话；裸演示头如为测试保留，必须显式开发开关且与真实认证验收区分。三个独立会话并不等于三个任意下拉角色。
- 保留旧 contracts；旧 Web/MCP/runner 的副作用要经过统一边界，或在明确比赛启动模式中默认关闭。不能仅保护新界面而让旧写路径继续绕过。用直调旧入口负向验证。

### 4.2 命令级源状态、版本和输入

- 为每个命令列允许的源状态及前置条件；通用状态图只作第二道守卫。accept/assign 只能 OPEN；reject_completion 只能 AWAITING_ACCEPTANCE；reassign 只 ACCEPTED/SCHEDULED；首次提议不改变为 SCHEDULED。
- 特别封堵：SCHEDULED 被另一个技工 accept；SCHEDULED 被报修人 reject-finish 直接变 IN_PROGRESS；CANCELLED 无提议还 reject appointment 并返回虚假的 ACCEPTED。
- 所有写命令实际使用输入模型；expected_version 必填严格正整数，不接受 null/bool/错误类型逃过校验；幂等键有非空与长度约束；缺字段给明确4xx而非500。
- 草稿可容纳缺信息，但提交前验证地点/服务空间同项目、联系人等业务必填项；失败保留草稿。分配、取消、退回等理由保存而不只回在响应。
- 任务更新、预约/事件/回执保持事务一致；并发写必须使用独立连接竞争验证，不能串行测试冒充并发。所有成功响应与数据库事实一致。

### 4.3 幂等、审计、迁移

- 统一覆盖 core/appointments/extended/all adapters，不能某些命令只依赖 UNIQUE 报错。
- 同一主体/幂等键的请求指纹涵盖项目、命令、对象、版本和规范化参数（附件含内容摘要）；同一请求重试返回原 action_id、原结果且不重复写；不同请求同 key 返回409。
- 在当前主体认证和回执访问授权后处理重放，不能因重放机制绕过撤销授权；成功重放不要被旧 expected_version 错误挡掉。
- 保存可审计失败尝试；失败审计不能与业务回滚一并丢失，也不能把失败留成成功回执。明确不可重试输入错误与瞬时错误语义。
- 版本化 schema 迁移支持空库与已有副本，备份可恢复。不能依赖 CREATE IF NOT EXISTS 自动升级旧列；消除 EXTRA_SCHEMA 双来源和 tx/executescript 事务问题；回滚异常不能吞原始原因。
- 所有新路径使用显式运行目录；线程/连接和后台任务生命周期要可关闭，避免测试污染现有 runtime。

## 5. 设备、预约、完工与附件

### 5.1 设备

- 普通编码走 asset_code；`asset:<asset_id>` 走稳定ID，两者解析同一设备；伪造/归档/跨项目拒绝。
- 补齐设备安装位置和有效服务空间关系，绑定必须满足服务关系；同安装位置不等于服务关系，不能拿仅增加字段代替校验。
- DRAFT 本人报修人；OPEN 经理；ACCEPTED/SCHEDULED 承接技工或经理；IN_PROGRESS 经理凭理由更正且保存旧/新值；AWAITING_ACCEPTANCE/终态不直接更换。
- 未绑定有效设备不能开工；未知主体不能 bind/unbind。设备详情展示编码、位置、服务空间与来源。

### 5.2 预约

- 首次提议保持 ACCEPTED；本人报修人成功确认才 SCHEDULED。改约期间保持 SCHEDULED 和旧 CONFIRMED。
- 确认时验证任务阶段、当前承接者、版本、有效期、时间和跨项目冲突；当前任务将被替换的旧预约排除于冲突检查，仍禁止与其他任务重叠；相邻半开区间允许。
- 拒绝/过期新提议保留旧预约且可正常开工；无旧预约才回 ACCEPTED。不存在/非有效提议不得返回成功；旧 proposal ID 不得错误确认新提议。
- 使用注入式服务端时钟覆盖过去、当前、未来、过期、时区；默认开始<=30天、15–240分钟、有效期min(24h,开始时间)按需求实现为配置，不把客户端当前时间当权威。
- 开工验证设备、承接者和确认预约，start<=now<end；开工使其他未确认提议失效，不能在已开工/终态迟到确认改变预约。
- 改派/取消事务中释放相关预约并处理提醒作业，旧技工再调用必须拒绝。

### 5.3 完工、验收、证据

- 完工记录有新的 completion_id、说明、处置方式、提交主体、时间、关联证据。退回后保留旧证据与轮次，二次完工有新ID；验收/退回关联具体轮次和版本并持久保存理由。
- 完工必须有本任务合法 READY 附件，至少验证实际存储存在且内容完整；其他任务/隔离/缺失或损坏附件不能提供虚假完成依据。
- 附件上传/下载/隔离授权统一；缺少 evidence_id 或属于其他任务不能产生成功回执。限制大小、内容类型及安全文件名；处理上传失败和DB回滚后的孤儿文件，采用可恢复的暂存/提交机制。
- 下载保留二进制字节和正确响应头，校验哈希；证据文件失败不导致“成功但无法回读”。为隔离/轮次定义事件与版本语义并测试。

## 6. Web、本地启动与原生

### 6.1 Web 全功能链和恢复

- 分开 proposedAppt/confirmedAppt，确认绑定 proposed ID；技工开工依据 confirmed ID。首次提议现在保持 ACCEPTED，前端也要跟着按提议事实显示确认入口，不能仍只判断 SCHEDULED。
- 补 quarantine 分发，未知 kind 拒绝而非 fetch(undefined)。经理分配按钮必须提供所需理由；所有实际按钮逐个核对API/请求字段/成功回读。
- 技工乙用项目数组/项目选择和 URLSearchParams，不再把 `prj-A & prj-B` 作为一个ID。
- 任务详情路由必须存在或重定向到实际页面并选中 task；收藏/通知/设备详情按基线补可用入口。
- task_id、version、表单与pending request同属明确状态对象；快速切换任务时忽略过期响应；不从DOM猜version=1。
- 每个逻辑写操作生成唯一key并保留到结果确定，丢响应用原key重试；按钮防重复、离线禁写、冲突回读，不自动覆盖用户输入。
- 代理处理 ConnectError/TimeoutException 和非JSON响应；binary透传；无后端有明确恢复提示，不以200包装错误。
- 先做三独立角色真实浏览器成功链，再做退回链、改约链和失败恢复；函数探针不能代替浏览器实际按钮验收。

### 6.2 启动、基线和工程文档

- 提供实际可运行的零参配置工厂或启动器，读取明确DB/evidence路径；文档命令原样可启动。统一端口配置，E2E用传入 BASE_URL/DB，不能硬编码连用户现有8713。
- E2E遇HTTP失败应退出非零，断言最后状态、回执、轮次、附件、预约、授权，而不只格式化JSON。单次脚本成功不等于重复运行幂等/恢复通过。

- 版本字段、实际路由、schema、命令/查询计数统一；当前实现契约独立版本化，保留历史设计。不得靠把设计要求删成当前弱实现使文档一致。

## 7. 不得漏掉的已有P0能力

缺失功能不能以“这只是修bug”为由忘掉，应按L0–L7和依赖推进：

- SSE只作授权的变更提示，重连游标/全量回读不会重放写命令；断线期间的状态恢复可验证。
- 提醒作业持久化、重启恢复、去重；改约/取消后旧作业不误触发，验收超时只提醒不自动验收；只有站内通知，无外部短信/消息。
- 三条真实AI链：草稿字段、设备历史建议、阶段说明。保留原文/来源/缺字段，输出严格校验且不直接写业务状态；失败有人工兜底。
- T33–T38：同意图不同表述、未知/歧义/错误引用、生成时改派改约后的旧建议失效、工具白名单、无回执不得声称成功/回读超时待核验、保存模型/提示/数据/宿主版本且隔离仿真真值。
- 外部工单未配置时零外部请求、无external_id、无虚假SUCCEEDED；本地业务仍独立可验收。测试可用假接收端，必须标明非真实对外完成。

真实模型或宿主不可用时，离线单测可以验证接口和兜底，真实项目保持 NOT_RUN/FAIL/BLOCKED（按实际），不能一并标 PASS。

## 8. 必须执行的验证与证据规则

1. 修复前复现旧 probe 与新 probe_extra，保存实际输出；它们是诊断程序，不要求修复后仍能一路执行到末尾（修复权限后原先利用漏洞的铺垫会失败）。把反例转成符合基线的正式测试，合法夹具走真实允许路径。
2. 权限/状态做命令×源状态×主体关系的参数化矩阵，覆盖上面所有绕过；不只写一个happy path。
3. 并发：独立DB连接的抢单、同技工跨项目预约确认、幂等重复提交；断言仅一份业务效果和相符回执，不只是HTTP码。
4. 恢复：回执响应丢失、过期版本、服务端异常、附件失败、事务中途故障、重启后任务/预约/收藏/通知/完工轮次回读。

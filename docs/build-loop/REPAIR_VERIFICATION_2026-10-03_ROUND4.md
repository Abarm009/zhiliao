## 2. 剩余问题与修改建议

### R4-01 [P1] Web 设备候选查询传错协议，按钮出现但仍无法绑定

位置：`app/demo-web/static/workbench.html:611–624`；`backend/src/octosense_backend/extended.py:137–161`。

`fetchCandidates()` 把 `as-a-1/as-a-2/as-a-3` 当作普通 `code` 传入 /assets/match。接口约定普通 code 按 asset_code 查找；稳定 ID 必须使用 `asset:<asset_id>`。本轮三条查询均 **404**，正确 `asset:as-a-1` 和 `AC-001` 则 **200**。

真实浏览器从新建走到 ACCEPTED，点击“绑定设备（按服务关系选）”，弹出“当前任务空间没有可服务的设备”，任务仍无设备。异常被 catch 吞掉后变成错误的“无设备”提示。技工与经理绑定函数共用此查询，经理入口有同一问题。

查询还硬编码三个 A 项目资产，没有按实际任务空间筛选服务关系；仅补 `asset:` 能解决当前编码错误，但不能完成“按项目和服务空间选设备”的要求。

**建议：** 提供按授权项目与任务服务空间获取候选的接口，或正确使用现有查询并严格验证服务关系；移除硬编码资产清单，区分无候选与查询失败。真实浏览器从绑定继续跑到验收后才能关闭 R3-03。

### R4-02 [P1] 修改草稿空间未重新校验已绑定设备，能够提交矛盾任务

位置：`backend/src/octosense_backend/commands/__init__.py:362–387`；confirm_draft 的提交检查 432–450。

独立复现：DRAFT 在会议室 `sp-a-1` 绑定 `as-a-1`，随后 update_draft 把空间改为配电间 `sp-a-3`。编辑返回 **200**，设备仍是 as-a-1；该设备与新空间无服务关系。继续 confirm 返回 **200**，任务进入 OPEN。

update_draft 文档字符串声称会保持设备服务关系，但实现只验证空间存在于项目。事务和幂等已修复，不代表业务不变量已完整校验。

**建议：** 修改空间时验证已绑定设备是否服务新空间；不符合则拒绝并保持原状态，或按明确产品规则提示重新选择设备并事务化处理关联变化。提交前再检查最终关系。回归同时断言空间、设备、版本、事件和回执，不能只测跨项目空间拒绝。

### R4-03 [P2] allowed_actions 与执行权限仍矛盾，Web 也未实际消费该集合

位置：`backend/src/octosense_backend/api/__init__.py:857–868`；`app/demo-web/static/workbench.html:199,253–338`。

独立实测：

- IN_PROGRESS 的承接技工收到 allowed_actions 包含 unbind_asset，执行却 **403**；基线只允许经理凭理由修改。
- ACCEPTED 的报修人收到 allowed_actions 包含 cancel，执行却 **403**；基线只允许报修人取消 DRAFT/OPEN。

后端拒绝符合基线，此处不是授权逃逸，而是动作声明和界面行为错误。Web renderActions 仍根据 me.role/status 手写规则，没有接收 detail 的 allowed_actions；报修人在 ACCEPTED/SCHEDULED 仍显示取消按钮。修复报告“Web 与后端共用同一矩阵”的表述不符合当前代码。

**建议：** 共用可复用的阶段/主体策略生成动作集合，Web 以服务端集合控制动作，再按必要前置条件提示；领域执行继续强制授权。增加“声明可执行的动作与实际执行结果一致”的角色/状态矩阵测试，同时保留不合法动作的拒绝测试。

### R4-04 [P1] Web 上传证据仍是硬编码图片，没有用户文件选择

位置：`app/demo-web/static/workbench.html:523–538`。

静态确认：uploadEvidence 没有文件输入/选择流程，每次点击都解码硬编码 tinyPng，构造 Blob 并上传，随后提示“证据已上传”。这些字节可以被后端真实保存并校验摘要，但并不是用户选择的现场证据。

这是仍未处理的既有演示实现，不是本轮新引入的回归。它不满足第四轮 R3-03“真实文件证据”的浏览器验收。本轮真实 UI 停在绑定处，没有声称实际点击上传，也没有用静态发现冒充动态结果。

**建议：** 接入实际文件选择、校验与上传进度，显示所选文件名及成功/失败，提供授权下载回读；测试至少两份不同文件，核对原始字节与下载字节一致。演示图片若保留应明确标识且不能冒充真实证据通过验收。

### R4-05 [P1] 原生提交与包准入仍失败；源码搜索探针不能证明宿主阻断

位置：`app/bundle/main.splash:303–315,558–580`；`app/bundle/manifest.json`；`app/docs/round4_native_probe.py:52–78,83–107`。

本轮对当前原始包执行 Hub 检查：实际 digest 为 `81da85ab203fbe01daad8b397d8d4e854dd57406533cb816a0c83ecf46482b8d`，manifest 仍为 `c066a517776438e1e4593f3f106f6a5ba24c5eb6668be7e18a2bded4bdbbaf82`，结果 REFUSED。

将当前包复制到隔离目录重新打戳，固定 card-host 确实可显示、可创建 DRAFT。但本轮真实点击“提交报修”后仍 DRAFT，没有提交回执；日志再次出现 `no getter for field id on type nil` 和 `call target is not a function (got nil)`。日志行号可能受包装偏移影响，不能直接认定错误根因。

本轮改为 `ready:false` 阻止伪附件完工是正确改进，但真实文件获取/读取/摘要链路依然没有接通。失败时还会新增 pending 元数据并增加任务版本，不能称“上传能力已实现”。

新的“原生能力探针”有明确证据缺陷：

- 通过搜索应用有没有 picker 词来推断宿主是否提供文件选择，不能证明能力不存在；注释里的词也参与匹配。
- 搜索 `settle(` 就认定统一命令守卫已声明；当前该字符串仅出现在 main.splash 顶部两行注释。实际函数名是 runCommand，其正确性应通过执行证明。
- 计算的是单个 main.splash 的 SHA-256，却拿来与 manifest 的 bundle BLAKE3 声明比较。这不是 Hub 包摘要验证方法，不能据此解释 digest 不符。
- BLOCKED 不计失败且整体退出 0，只能描述该脚本的有限检查，不能作为原生准入/动作通过证据。报告一面写 R3-08 BLOCKED，一面把 V01 标“仍 PASS”，互相矛盾。

**建议：** 使用 Hub 实际摘要工具处理最终交付目录，原件本身检查通过；在固定宿主上按最小脚本定位 nil 调用，文件选择/二进制存储/摘要能力分别做运行探针。不要将按钮布局缺口自动当成提交调用失败根因。应用级修复和本地重新打戳已列入第四轮执行指令，无须把这些工作归为“等外部发布授权”。真实能力不足的项仍需明确证据并保持未完成。

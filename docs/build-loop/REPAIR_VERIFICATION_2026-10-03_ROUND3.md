## 二、当前缺陷与修复建议

### R3-01 [P1] 新增草稿编辑接口没有幂等检查与事务，500 后数据已经提交

位置：`backend/src/octosense_backend/api/__init__.py:213–291`，尤其 222、253–284；连接配置 `db/__init__.py:265`。

实测同一草稿：第一次编辑 200；完全相同请求重试返回 409 VERSION_CONFLICT，未回放原结果。随后使用当前版本、同一个幂等键和不同联系人编辑，返回 **500**，但数据库联系人已变为新值，version **2→3**，新增编辑事件；只有原先 1 条成功编辑回执，已经有 2 条编辑事件。

根因：新路由明确绕过 `_run`，先更新任务/写事件，最后直接插回执，没有 `check_replay`。`isolation_level=None` 实际是自动提交，代码注释“autocommit off”和空的 `with conn: pass` 不会把先前写入纳入事务。重复键导致最后的回执插入失败，前面的数据没有回滚。版本检查与 UPDATE 也不处于同一事务，存在并发覆盖风险（本轮未另做并发复现）。

**修改建议：** 将 update_draft 做成统一领域命令，事务内执行当前授权、幂等检查、版本校验、任务/事件/回执写入；使用统一时钟，不直接 time.time。原请求回放同 action_id/结果，冲突 409 且没有业务变化。新增相同请求、同键不同载荷、回执写入失败、并发旧版本回归。不能只捕获 IntegrityError 后改状态码。

### R3-02 [P1] 统一授权仍只补了个别方法，撤权后有四条写路径成功

位置：`commands/__init__.py:227–262,669–740`；`extended.py:190–196`；`api/__init__.py:225–237`。

每个反例均在独立数据库构造：原报修人保留 B 项目身份、从 A 项目移除。A 任务详情返回 404，但：

| 写操作 | HTTP | 实际变化 |
|---|---|---|
| `/tasks/{id}/draft` | 200 | 草稿联系人改变，version=2 |
| DRAFT `/bind-asset` | 200 | 设备绑定，version=2 |
| DRAFT `/cancel` | 200 | 进入 CANCELLED |
| AWAITING_ACCEPTANCE `/reject-finish` | 200 | 进入 IN_PROGRESS |

本轮确实修好了 create_draft 撤权回放和 record_progress 的原漏洞，但 `_run` 仍主要在回放路径做统一对象授权；首次执行继续依赖各 body，部分分支只认 reporter_id。

**修改建议：** 在首次执行与回放共同入口校验当前项目成员/对象权限，再执行命令级角色与关系规则；包括新草稿编辑与 DRAFT 绑定。做全部命令撤权矩阵，保留另一项目身份以避免测试仅因“用户不再注册”提前拒绝。失败时不写业务状态、业务事件及成功回执，独立失败审计按设计保留。

### R3-03 [P1] Web 权限按钮没有同步，新主链卡在设备绑定

位置：`app/demo-web/static/workbench.html:244–323`，尤其 257–259、283–292；新增表单 25–29 与 createDraft 354–376。

本轮真实浏览器成功创建并提交 OPEN、由技工甲接为 ACCEPTED。此时设备为空：

- 技工界面只有“提议预约”，没有合法的绑定设备入口。
- 经理界面只有“改派给另一技工”“取消任务”，同样没有绑定入口。
- 报修人界面仍显示“绑定设备 AC-001/PWR-001”，实点返回 `PERMISSION_DENIED (actor needs one of ['MANAGER', 'TECHNICIAN'])`，任务仍 ACCEPTED、设备为空。

新后端权限拒绝是正确的，但前端只给错误主体提供按钮。页面还在提示“需 reporter 绑定”，没有使用后端 allowed_actions。空间表单修复有效，不等于 Web 主链已经通过。

此外静态确认：历史草稿补空间仅新增 API，页面没有 `/draft` 编辑入口；任务类别没有选择字段，也没有在创建请求中传 category。两者均未达到 R2-03 的完整标准。

**修改建议：** 按实际主体与后端动作集合提供设备选择/绑定/更正；补草稿编辑和类别输入，移除错误提示及非法按钮。以浏览器完成原定三角色全链，不能在 API 链里手工绑定后声称页面已完成。

### R3-04 [P1] 历史建议接口仍返回未经脱敏的事件，联系人旁路泄露

位置：`backend/src/octosense_backend/extended.py:599–641`，尤其 630–641；API history-advice 路由 535–539。

创建含 `private-contact` 的 OPEN 任务，以未承接的技能匹配技工调用 `/tasks/{id}/history-advice?asset_id=as-a-1` 返回 **200**，响应原始 events.after_state 中仍包含联系人。相同主体的任务详情 contact_info 已为 null。

修复仅覆盖了详情、事件轮询和 SSE 共用的 `_event_out`，历史建议直接返回 `dict(e)`，绕过该投影。

**修改建议：** 历史建议复用按主体授权的事件投影，保留内部原始审计但禁止原样对外；用同一唯一联系人标记覆盖所有读取入口，包括 asset_id 显式查询及旧事件。现有 detail/poll 正向修复不要回退。

### R3-05 [P1] 绑定矩阵已收紧，解绑仍允许报修人提交后改设备

位置：`backend/src/octosense_backend/extended.py:252–279`。

实测 OPEN 任务由合法经理先绑定 as-a-1，再由原报修人调用 unbind-asset，返回 **200**，asset_id 变为 null。解绑仍接受 reporter/assignee/manager 的大集合，只对 IN_PROGRESS 额外限制经理，绕过同阶段绑定规则。

**修改建议：** 绑定、更正、解绑共用阶段权限策略，按基线区分 DRAFT、OPEN、ACCEPTED/SCHEDULED、IN_PROGRESS 和终态；对同一个矩阵测试两种入口，拒绝时设备/版本/事件不变。

### R3-06 [P2] 作业积压到开工后仍发送“1 小时后开始”的过期提醒

位置：`backend/src/octosense_backend/jobs.py:24–28,157–169`。

实测正常预约并开工进入 IN_PROGRESS 后，第一次执行到期作业，仍发出 **2 条 APPOINTMENT_UPCOMING / APPOINTMENT_UPCOMING_REPORTER** 通知，正文说“将于 1 小时后开始”。当前状态表主动允许 IN_PROGRESS 和 AWAITING_ACCEPTANCE 发送这类提醒；执行时只按状态检查，没有验证预约时效、当前有效预约及正文是否过期。

已完成任务不再催办的原反例通过，但不能代表开工、重启积压等生命周期都已修好。

**修改建议：** 开工时取消开始前提醒，执行时再检查当前有效预约和时刻；已过开始时间不能继续发送未来时态的开始前通知。验收提醒同样检查当前完工轮次，不能只保存 round 却不核验。覆盖停机后恢复、延迟 tick 和状态转换。

### R3-07 [P1] 已撤权报修人仍收到并读取该任务的新提醒

位置：`backend/src/octosense_backend/jobs.py:146–169`；`api/__init__.py:738–751`。

实测预约确认后将报修人从 A 移除、保留 B 身份，在提醒到期时运行作业：A 任务详情 404，但 `/notifications` **200**，返回新创建的 A 任务提醒、任务 ID 和提醒正文。执行器只看 payload.user_id 和任务状态，通知列表也只按 user_id 查询，没有当前对象授权。

**修改建议：** 作业发送前验证接收者当前项目/对象权限，失效接收关系取消对应作业；通知读取执行适当的对象权限策略。此反例是撤权后新生成通知，不涉及必须删除已有历史审计的争论。增加“保留 B 身份、撤销 A 权限后不再产生/泄露 A 新通知”的回归。

### R3-08 [P1] 原生两项未处理，宿主阻断的根因结论没有新增实证

位置：`app/bundle/main.splash:303–315,558–574`；`app/bundle/manifest.json`；本轮修复报告 §二/五。

源文件哈希确认原生 bundle 相对上轮复查完全未变。当前原包仍因摘要不符被 Hub 拒绝，虚构 bytes/sha/ready 的证据逻辑也仍在。修复者如实写了“本轮未运行 card-host”，因此只能认定未修复，不能据此确认 nil 函数调用是 set_visible/on_render 导致，更不能认定升级宿主就是必要解法。

“宿主不开放隔离存储 API”的表述也过于宽泛：应用本身已有 fs.write/read 落盘任务的代码与上轮实测。真实文件选择/二进制附件能力是否不足，需要分别做最小能力探针，不能把 picker、隔离存储与按钮重排混为同一阻断。

**修改建议：** 先在既定宿主复现实际动作调用失败，定位脚本调用链；独立验证文件获取、二进制读写、摘要能力。能在应用内解决的继续修，真正缺少能力的附最小复现。最终更新实际交付包摘要并验证，不以副本打戳成功代替原件准入。

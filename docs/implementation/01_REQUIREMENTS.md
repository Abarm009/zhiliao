## 1. 交付目标与事实归属

比赛作品让报修人、维修技工、项目经理围绕同一项维修完成“报单—接单—设备绑定—预约—处理—完工—验收”。必须有真实持久化状态及角色操作，不以播放脚本或前端计时动画替代。AI 实接模型参与信息理解、工具检索、提出建议和解释进展。

本轮本地维修任务是事实；外部工单仅提供扩展契约，默认未配置。桌面卡必须同时展示本地任务状态与“外部工单系统未接入”，外部未接入不阻断本地闭环。以后接入外部系统须迁移项目的数据权威模式，不自动改变历史任务。

## 3. 用户与权限

角色来自服务器会话和项目授权，不能相信请求体的角色或 user_id。一个用户可拥有多个项目角色；执行权限按当前项目核验。

|动作|REPORTER|TECHNICIAN|MANAGER|
|---|---|---|---|
|创建草稿/提交报单|自己的任务|可作为报修人创建自己的任务|可作为报修人创建自己的任务|
|查看任务|自己的任务|本项目技能匹配的 OPEN；自己承接的任务|授权项目全部任务|
|查看 OPEN 任务敏感联系方式|否，除自己|接单前隐藏|授权范围内可见|
|自主接单|否|本项目、技能匹配、任务未被承接|如另具技工角色才可自主接单|
|分配/改派|否|否|同项目具有有效技工角色、技能匹配的人选|
|确认设备|草稿中选择；提交后不可擅改|当前承接者可按状态规则绑定|所辖项目可按规则绑定|
|提议预约|只填写时间偏好|当前承接者|代提议并记录操作者|
|确认/拒绝预约|该任务报修人|不得代报修人确认|P0 不代确认预约|
|开工/进度/完工|否|当前承接者|如本人非承接者，不得伪装技工报完工|
|验收/退回|该任务报修人|不得自我验收|可代验收/退回，理由必填|
|取消|自己的 DRAFT/OPEN|否|DRAFT/OPEN/ACCEPTED/SCHEDULED/IN_PROGRESS，理由必填|
|置顶/取消置顶|自己有权查看的任务|同左|同左|

P0 演示至少三类服务器账号，支持三个独立浏览器会话。界面下拉切角色仅可作为开发调试能力，不算身份校验。正式发布前另接生产认证与组织隔离。

## 4. 正常业务旅程

1. 报修人打开宿主内维修入口，选择项目，输入“东侧会议室空调不制冷，希望明天下午处理”。
2. 创建 DRAFT；Agent 提取候选地点、症状、设备、时间偏好。每项显示原文/台账来源；歧义要求选择，不自动猜定。
3. 报修人确认地点、问题、联系方式与信息使用范围，点击“提交报单”，获得本地任务号，状态 OPEN。
4. 具有对应项目权限和维修技能的技工接单，或经理明确分配，状态 ACCEPTED。
5. 不确定设备时，承接技工依据现场编码或台账确认主设备。绑定后可回读设备档案与任务引用。
6. 技工参考时间偏好及自己的已确认预约，提出明确起止区间；报修人确认成功后状态 SCHEDULED。
7. 承接技工在约定区间内开工，状态 IN_PROGRESS；记录到场检查、处理说明与必要附件。
8. 技工提交完工说明及证据，状态 AWAITING_ACCEPTANCE；报修人确认问题已解决，进入 COMPLETED；未解决则填写理由退回 IN_PROGRESS。
9. 各角色列表与卡片均从服务器回读同一任务；重启/重登后仍能看到进度。外部工单号为空，显示未接入。

## 5. R01 报单详细规则

- 必填：项目、问题原文、已确认服务空间、症状类别、报修联系人；设备可暂未确认。
- 用户可不懂设备名称，但不能提交不存在或不在项目内的空间。无可匹配空间时保留草稿，提示人工处理，不悄悄建到默认地点。
- 问题原文保留；AI 摘要另存，人工修改不覆盖原始来源。
- 文本长度默认 1–2000 字符；联系人显示名与联系说明为字段，P0 不强制某个国家手机号格式。
- 创建草稿及提交分别幂等。源事件重复投递返回同一草稿；相同文本的新事件不自动合并。重复故障只提示关联历史，不阻止新报单。
- 历史关联只允许同项目可见任务；引用来源可点击。新任务与历史单号不能混用。
- P0 症状采用稳定内部枚举 `HVAC_NOT_COOLING / WATER_LEAK / ELECTRICAL / OTHER`；和旧 ops 枚举通过显式映射转换，不改旧枚举。

## 6. R02 接单与改派详细规则

- OPEN 才能首次接单。两个技工同时接单，只有一个成功，另一个收到冲突并刷新当前承接者；不能先响应成功再后台覆盖。
- 技工只能代表自己接单。经理分配必须给出同项目有效技工与理由，事件显示“经理分配”，不是“技工自主接单”。
- 经理仅能改派 ACCEPTED/SCHEDULED 的未开工任务；新承接者重新安排预约。旧确认预约释放，旧提议取消，状态回 ACCEPTED。
- IN_PROGRESS 禁止直接改派；经理先记录现场处置并取消或由后续版本提供正式交接流程，不在 P0 静默换人。
- 不实现自动接单倒计时。可以提醒待接单，不能把超时提醒写成已经派工。

## 7. R03 设备身份详细规则

- 稳定身份为 `asset_id`，同时保存 `project_id / asset_code / source / source_ref / display_name / category / active`；同项目 asset_code 唯一，source 为 DEMO/LOCAL_IMPORT/EXTERNAL_SNAPSHOT。
- 区分设备安装位置与服务空间；空调可能安装在机房、服务另一个房间。绑定依据有效的“服务空间—设备”关系，不仅检查安装位置相同。
- 二维码载荷为本应用生成的 `asset:<asset_id>`；解析后再通过当前用户权限读取台账。不得直接执行二维码中的 URL、脚本或 SQL。
- 可输入完整编码或粘贴二维码载荷；同名多候选列出编码/位置/项目，不用模型置信度替代人工确认。
- 提交报单可以无设备；开工前必须绑定一个有效主设备。P0 一任务一主设备，多设备故障拆成关联任务。
- 绑定记录包含绑定人、时间、依据（台账选择/现场编码），不代表已经完成硬件真实性认证。
- DRAFT 由本人报修人选择，OPEN 仅经理绑定；ACCEPTED/SCHEDULED 由承接技工或经理绑定或更正；IN_PROGRESS 仅经理凭理由更正并保留旧值；完工待验收后不直接改设备，应退回后更正。
- 已归档设备保留历史详情，但不可新绑定；外部设备刷新不得修改稳定本地引用。

## 8. R05 预约详细规则

- “明天下午”只属于偏好；界面必须显示推导日期及 Asia/Shanghai 时区供用户核对，不能直接确认成预约。
- 产品默认值（可配置，非赛事规则）：预约开始在当前时间之后且不超过 30 天；时长 15–240 分钟；提议有效期为 `min(提出后24小时, 预约开始时间)`。
- 同一任务最多一个有效 PROPOSED；新提议将旧提议 SUPERSEDED。
- 新提议不预占技工资源。确认时检查当前承接者、任务版本、提议有效期和时间冲突；采用半开区间 `[start,end)`，相邻不冲突。
- 冲突条件：同技工、同组织内全部项目、CONFIRMED 预约满足 `existing.start < new.end AND existing.end > new.start`。事务内排除同任务将被替换的旧预约；返回不含其他任务隐私的“该时间不可用”。
- 改约时原 CONFIRMED 仍有效，直到新提议确认成功后原记录 SUPERSEDED；拒绝或过期新提议不取消原预约。任务保持 SCHEDULED。
- 第一份预约被拒绝/过期时任务仍 ACCEPTED。提议拒绝理由必填。所有状态变更保留记录。
- 开工要求存在当前承接者对应的有效确认预约，`start <= now < end`，并已绑定设备。开工时将其他未确认提议 SUPERSEDED，防止迟到确认改变已开工任务。
- 预约结束仍未开工时显示“预约已超时，需重新预约”，不自动标记完成；确认新预约后才允许开工。处理超出原结束时间只显示超时，不自动停止维修。
- 所有时间由服务端时钟核验，UTC 毫秒持久化；客户端时区只影响展示，禁止通过请求覆盖业务当前时间。

## 9. R04/R06 桌面与进度

页面与视觉实施以[UI与交互规范](10_UI_UX_SPEC.md)为补充：强调角色化待办、同卡持续更新、可编辑Agent建议、可恢复异常和原生桌面质感。其U01–U12是专项验收，不改变本文件权限或任务状态。

P0 页面：`维修首页`（我的报修/待接单/我承接的/经理项目视图）、`报单草稿`、`任务详情卡`、`设备身份页`、`预约面板`、`通知列表`。这些是同一应用的页面，不另建桌面壳。

任务卡必须展示：本地任务号、问题/设备/空间、当前阶段、承接者、预约起止时间与确认状态、下一步由谁处理、最近更新时间、来源标签、外部同步状态、当前角色允许的动作。共享链接只带 task_id，不携带账号凭据，不自动赋予阅读权限。

- 桌面收藏/置顶保存为“用户—任务”记录。含义是宿主内应用首页排序，不宣称系统级置顶窗口。
- 不提供随意填写的 0–100% 进度。用确定的业务阶段和带作者/时间的处置事件表示进展。
- 处置事件子类：`INSPECTION / REPAIR / WAITING_PARTS / NOTE`；WAITING_PARTS 是 IN_PROGRESS 的说明，不新增隐式状态，不自动采购。
- 操作期间按钮禁用，成功后按服务端任务版本回读；网络错误保留相同幂等键用于重试。
- 列表首次用 HTTP 快照，后续 SSE 仅作为变更提示；收到事件后取最新投影。重连用游标；游标过旧全量刷新。浏览器离线时标明缓存时间并禁用写操作。
- 无权限、无任务、加载中、离线、操作冲突、预约冲突、模型错误、附件失败必须有明确界面，不使用永不结束的加载动画。
- P0 通知为应用内持久化通知；系统通知、短信、企微消息均未接通，禁止显示送达。

## 10. R07 完工和验收

- 完工必须有处置说明及至少一份当前任务可读的证据附件，设备必须已确认。P0 附件限制 JPEG/PNG/PDF，单件不超过 10 MiB，单任务最多 10 件；验证真实文件类型、文件大小与所属任务。
- 完工记录保留真实填写者、时间、处置内容、附件引用；根因可为 UNKNOWN，不要求模型编造诊断。
- 报修人验收写入验收记录。经理代验收额外记录 `on_behalf=true` 与必填理由；技工不能自验。服务器强制验收/退回操作者不等于当前承接者，多角色用户也不例外；报修人与承接者相同时，必须由另一位经理代验收。
- 验收退回填写问题说明，任务回 IN_PROGRESS，保留前次完工证据和验收失败记录，可再次提交新的完工记录。
- COMPLETED/CANCELLED 不可直接修改历史状态；再次故障创建新任务并可关联历史任务。P0 不做关闭后重开。
- 验收超时只提醒，不自动确认通过。

## 11. R08 Agent 可观察行为

三条必测模型链路：① 原话→字段建议→人工确认；② 接单后读取设备/历史/预约占用→有来源的建议；③ 处理事件变化→基于最新任务的阶段说明和下一步建议。

模型输出包含结构化建议、证据引用、缺失字段，不直接替用户确认。后端输出校验失败可限定一次修复重试，仍失败转人工表单。保留模型/提示版本、工具结果来源、运行耗时和失败；不需要对终端用户展示内部推理。

当设备/时间存在歧义、资料不足、外部系统未配置时，输出相应未知。带指令的用户文本/历史记录不能改变系统权限。阶段摘要不能覆盖数据库投影。

## 12. 完成定义

每一项 R01–R10 都必须有可复现验收证据；P0 桌面宿主、真实模型、本地业务持久化分别验证。外部工单明确未接入不扣成本地任务未实现，但不能自行保证赛方一定接受任意演示数据：按 [官方合规矩阵](06_OFFICIAL_COMPLIANCE.md) 与指定环境验收。

所有新增时间/大小阈值均为本包产品默认值，不是当前代码事实或比赛硬要求。编码前发现不可实现约束时提交设计变更，不能默默删掉用户要求的功能。

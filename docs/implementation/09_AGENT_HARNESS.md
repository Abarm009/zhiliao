## 1. 三种“完成”分别定义

|对象|何时算完成|不能采用的替代证据|
|---|---|---|
|模型运行|输出符合schema，引用可解析，工具错误清楚呈现|LLM结束、stream关闭不等于动作成功|
|一次业务动作|统一执行器提交回执，持久化事实可回读且满足该动作后置条件|文本说“已预约”、HTTP200或绿勾不够|
|维修任务|技工真实提交完工证据，独立报修人/经理验收，状态COMPLETED|创建工单、Agent自评、技工自己点完成不够|

开发过程中的“编码模型说做完”同样只能进入待复验；不因此发布、推送或宣称比赛通过。此处借鉴双环职责，不直接调用或安装OctoLoop。

## 2. AgentRuntimePort

拟新增application/agent_runtime.py定义内部端口；已有agent_service通过它运行模型。默认适配本地已有llm/client和必要的ops/agent机制，禁止直接复用旧runner的自动写路径。

输入由服务器组装：run_id、purpose、可信actor_scope、task_id、base_task_version、服务端时间、可见任务/设备/历史快照、能力清单与预算。模型不能提交actor_scope、now、数据库路径或工具URL作为可信值。

能力默认只读：定位空间、列候选设备及服务关系、查可见历史、召回有来源经验、读当前任务与可公开预约可用性。禁止旧create_workorder、notify、write_memory作为裸模型工具。

输出：结构化建议、引用ID、缺失信息、单条suggested_command或空值。一次只提出当前阶段可执行的动作；多步流程由持久化任务驱动，不能预先批准“自动跑到验收”。

本轮固定一个运行适配器；后续若接octos，其模型/工具调用仍被同一端口限制。更换供应商只更换配置与适配器，不能改变权限、状态或真值。开发用Codex Router与产品运行模型分开配置。

## 3. IntentSpec v0.1：内部产物，不新增外部API

利用repair_agent_runs.result_json存储内部建议结构，GET agent-runs沿用现有AgentRun公开字段。新增内容由服务端编译成当前公开summary、missing_fields、evidence_refs、suggested_command；内部字段不直接穿透额外输出。

|字段|谁生成|规则|
|---|---|---|
|spec_version / run_id / task_id / base_task_version|服务器|与已保存run绑定，不接受模型覆盖|
|goal_kind|模型建议、服务端校验|REPORT_REPAIR / REPAIR_ADVICE / CHECK_PROGRESS；与purpose对应|
|candidate_fields|模型|草稿字段、候选asset/space及依据；不覆盖用户确认值|
|missing_fields / ambiguities|模型建议、规则复核|未知就补充，禁止默认填一个设备或预约|
|evidence_refs|模型引用、查询层核对|只能引用本次获授权工具返回的可解析对象；不存在则拒绝该建议|
|proposed_command|模型建议、编译器校验|仅现有TaskCommand枚举；不能把建议视为用户授权|
|view_recipe|确定性编译器|根据状态/角色/缺字段从白名单组件选择，P0模型不生成任意可执行代码|
|verification_recipe|确定性规则|按动作类型选择固定后置条件，模型不能放宽完成标准|

P0界面随意图和状态选择“补地点/选设备/看依据/预约确认/进度/验收”等已注册片段。原生宿主实现这些片段的真实控件与绑定。尚未验证的动态L0加载不得绕过固定app_id/version/digest；若课程包提供受控编译能力，再以独立设计变更接入。白名单组合不应对外宣传为任意应用代码生成。

业务事实（状态、设备、预约、进度）始终由TaskProjection和授权查询绑定；模型生成的解释须标为建议，有引用入口。不能将模型输出字面量伪装成实时业务值。

## 4. 从建议到动作的完整执行

1. 保存模型运行基础版本；取授权范围内的数据；模型提出建议。
2. 校验字段schema、引用存在性、项目范围、基础版本、当前角色动作。错误最多一次修复重试，失败回人工表单并记录错误。
3. 展示具体对象、字段、变更与来源。报修人/技工/经理按职责确认；同一账号不能凭切换角色越权。
4. 服务端按当前版本重建合法命令，使用幂等键调用统一execution。未来自动执行也必须有显式、限范围、可撤销授权，P0不新增自动写授权模式。
5. executor在单事务内写任务、预约/证据引用、回执和事件，禁止模型或外部网络占用写事务。
6. verifier独立读取动作回执和已提交事件，核对该命令后置条件；再取得最新角色投影展示。verifier是确定性代码，不能信任执行Agent的summary。
7. 后续版本变化使建议过期；应用持续读同一task_id，不重新从聊天猜进度。

## 5. Verifier与故障语义

拟新增application/result_verifier.py。最小检查：

|动作|动作版本必须证明的事实|
|---|---|
|submit_report|DRAFT转OPEN，提交者正确，任务号存在，必填字段完整|
|accept_task / assign_task|指定动作事件记录正确操作者/承接者，单一承接，任务版本递增|
|confirm_appointment|引用提议转CONFIRMED，旧确认原子替换，提交时无冲突，事件和task_version相符|
|start_work|开工事件对应有效预约和主设备，状态转IN_PROGRESS|
|submit_completion|完工记录与READY附件归同任务，转AWAITING_ACCEPTANCE|
|accept_completion|验收引用最新完工，验收者独立，转COMPLETED|

已提交动作可能在回读前被下一动作推进，不能要求“当前状态必须永远等于这次目标状态”。先用action_id、task_version和不可变事件核对当次结果，再显示当前最新投影。事件应保存该动作关键前后值/相关对象ID；不向无权限角色暴露原始审计负载。

验证读取暂时失败时显示“动作已有回执，结果核验待恢复”，保留原幂等键；不能回滚已提交事务、改成业务CANCELLED，或重新建单。核验不一致则记录告警并停止后续自动建议，交人工核查；不由模型自动补写使结果看似一致。

## 6. 历史经验与可信反馈

保留旧L1事实、L2事件、L3经验区分。当前诊断建议必须显示来源类型、时间、适用设备/空间和不确定性；历史经验不等于本次根因。

P0反馈保存处置、附件、UNKNOWN或人工确认根因、验收者与事件。仅查得到新的已验收历史，就已形成可解释的后续参考；不需要声称模型权重学习。旧verify_memory_prediction不能直接接受模型自报actual_root_cause当真值。

学习效果另设门：隔离测试故障 → 首次建议 → 独立可信结果 → 有版本的经验更新 → 同条件留出集复跑。没有完成该链路，不说“自动学习已验证”。

## 7. 冻结评测与开发交接

拟新增evaluation/，只存明示合成场景及测试代码；预期根因/权限/状态断言仅供评测器使用，不进入Agent检索或工具目录。运行输出放runtime/evaluation/。这些目录当前只是设计路径，不创建空目录冒充能力。

每次记录code revision或源码包SHA、host版本、app摘要、fixture版本、provider/model、prompt版本、时钟、工具权限、原始输入、ActionReceipt、事件、验证结果、用量和错误。没有官方统一模型名称时不写K3为固定ID；用可配置模型端口与同一案例比较。

新增以下待执行用例，补充原T01–T32：

|用例|期待行为|
|---|---|
|T33 意图泛化|同一维修意图的多种说法得到同一类合法操作；不同地点/症状不能强行归成同一模板|
|T34 依据缺失|未知空间、多个设备候选、无历史经验时主动补充；引用不存在则拒绝建议|

以上是运行Harness的工程要求，不是新增官方评分条款。开发Harness的复验由主模型与测试承担；产品业务终验由人承担，两者证据分开保存。

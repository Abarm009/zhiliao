## 1. 设计目标与默认风格

产品定位为“围绕任务展开的原生协作工作台”。界面让人看懂问题、核对依据、完成当前动作，并持续追踪同一事项。交互与美观都是交付条件：原生控件能操作、状态能解释、信息有层次、异常可恢复。

正式视觉方向：石墨深色背景、浅色正文、薄荷绿主要动作，具体色值按15及04-graphite原稿。保留充分留白、精确对齐和轻边框；阴影克制。只实现这一套主题，不先做浅色再改暗色。基础参数已同步为石墨；新增状态色为设计初值，原生实现须测对比度。

首页首屏应回答：我有什么待办、哪件事需要我处理、下一步怎么做。任务详情首屏应回答：哪里出了问题、现在是什么阶段、谁在处理、约在什么时间、当前有哪些可做动作。上述目标需用实际任务观察验证，不能仅凭设计者评价打勾。

## 2. 三类用户的信息优先级

|角色|默认关注|首要动作|次级信息|
|---|---|---|---|
|报修人|我的报修、待确认预约、待验收|报修 / 确认预约 / 验收|设备详细参数、历史维修依据|
|技工|我承接的任务、当前预约、技能匹配待接单|接单 / 提议预约 / 开工 / 记录处理 / 提交完工|历史经验、设备服务关系|
|经理|项目内待分配、冲突、延期、待代处理任务|分配 / 改派 / 有理由代验收|人员任务与项目进度|

同一task_id共享事实，不同用户获得不同投影与操作。账号来自真实会话；多角色视图切换只切查询视角，不能增加权限或绕过“承接者不得自验”。经理不增加本轮未约定的全公司经营大屏。

## 3. 窗口与信息架构

使用官方宿主内的应用内容区，不绘制第二套操作系统标题栏。项目与账号入口简短稳定；切换项目后重查范围，不能继续显示前一项目的缓存详情。

以可用内容宽度选择布局（单位为逻辑像素，需Makepad实测）：

- 宽度≥1280：左侧导航约184，任务列表约320，右侧弹性详情；Agent依据在详情内折叠，不再加常驻第四栏。
- 宽度980–1279：导航收为紧凑图标加可展开文字；列表约280，详情占余量。
- 宽度<980或文字放大导致空间不足：任务列表和详情分级显示，返回时保留筛选、选中项与滚动位置。
- 操作区可吸附于详情底部，但必须预留内容空间；窄窗、文字放大和附件展开时不覆盖表单或错误提示。

信息架构：工作台 / 我的任务或项目任务 / 设备查询 / 通知。报单为明确主入口；预约和验收从任务内打开，不要求用户跨多个模块找同一事项。收藏表示应用内个人任务排序，不宣传OS级窗口置顶。

## 4. 页面结构与完成条件

|页面/面板|内容顺序|关键交互|成功反馈|
|---|---|---|---|
|工作台|待我处理 → 当前预约/处理中 → 收藏与最近任务|选择任务在原位展开；筛选有可清除条件|详情与所选任务一致；返回列表保持位置|
|报单草稿|一句话描述 → 解析建议 → 缺失字段 → 提交前摘要|问题原文可看；候选地点/设备可选择；只追问缺失项|提交回读后显示本地任务号与待接单|
|任务详情|身份标题 → 阶段/下一处理人 → 当前动作 → 预约/设备 → 进度与依据|主动作与当前角色一致；历史信息渐进展开|同卡显示服务器最新阶段与更新时间|
|设备身份|设备名和编码 → 服务空间/安装位置 → 来源 → 可见历史|按编码/载荷查找；多候选并列对比；返回任务不丢上下文|人工确认绑定后展示设备及依据|
|预约面板|当前有效预约 → 新提议 → 日期/区间 → 确认/拒绝|原预约与新提议清楚并列；完整日期、星期与时区可核对|服务端确认后才出现“预约已确认”|
|处理与完工|本次记录 → 附件 → 处置说明 → 提交摘要|上传可见进度/失败重试；草稿处置内容不因上传失败丢失|完工回读显示“待验收”，不能显示“任务已完成”|
|验收面板|处理结果 → 证据 → 验收选择与理由|查看附件；接受或退回；代验收标明操作者和理由|接受后完成；退回后处理中，旧证据保留|
|通知|待处理事项 → 时间 → 当前状态|点击回到有权查看的任务；过期通知显示“已处理/状态已变化”|已读不改变业务状态|

没有现成API支持的聚合数量不作为首期必需项。可显示当前已加载条目数并注明范围，不从一页数据推导“全部待办”。预约面板先实现日期和起止区间，不扩成完整排班软件。

## 5. 任务卡的阅读与操作顺序

```text
东侧会议室 · 空调不制冷                 [预约待确认]
本地任务号 · 当前设备/待确认 · 最近更新

当前进展：技工已提出维修时间
下一步：请你确认预约

拟预约：完整日期（星期）14:00–15:00 · 北京时间
承接技工：姓名

[确认预约]   [时间不合适]                [更多]

设备与位置     处理进度     相关依据
Agent建议：摘要，可展开查看来源；不冒充已执行结果
外部工单系统：未接入
```

上图为结构示意，未指定真实人员或实际业务结果。展示状态分两层：任务阶段（如已接单）和待办说明（如预约待确认）；后者是投影的解释，不得新增一个偷偷写入数据库的任务状态。

单张详情有一个最突出的主动作，必要时配一个清楚的次动作。危险操作进入独立菜单或确认面板；取消必须说明后果并填写业务要求的理由。无权限操作通常不展示；属于当前用户但前置条件不满足的操作保留禁用态并解释原因。

|业务状态|主动作示例，最终由服务器allowed_actions决定|
|---|---|
|DRAFT|本人补充信息 / 提交报单|
|OPEN|匹配技工接单；经理可分配；报修人看到等待处理|
|ACCEPTED|承接技工先确认设备或提议预约；有有效提议时，报修人确认或拒绝|
|SCHEDULED|承接技工在有效时间内开工；未到时间显示具体时间说明；报修人可处理新改约提议|
|IN_PROGRESS|承接技工记录处理、提交完工；其他人看进度|
|AWAITING_ACCEPTANCE|合格报修人/经理验收或退回；承接者看待验收|
|COMPLETED / CANCELLED|查看记录和证据；可新建另一项报修，不提供重新开工按钮|

阶段条可分“报修—承接—预约—处理—验收”，同时显示精确当前文字状态；取消单独呈现。退回后保留历史节点和退回原因，不把时间线清空。禁止用任意完成百分比装饰进度。

## 6. Agent交互要求

自然语言输入与结构化字段相互配合。报修人先说问题，界面给出可编辑的草稿建议；确认时集中核对，不逐个字段弹窗询问。模型未配置/失败时人工表单仍可用，但界面明确本次没有获得AI建议。

三个信息类别要一眼可分：

- 已核对事实：普通正文，附台账/用户确认/任务记录来源。
- Agent建议：石墨次级表面背景与“建议”文字标签，附可打开的依据；不显示无来源的精确置信百分比。
- 待确认动作：明确对象、时间和变化，放在行动面板；只有授权角色可提交。

处理中反馈只根据真实运行事件显示，例如“正在查询设备”“已找到2个候选”；没有对应工具事件时只显示中性的“正在处理”。不播放预写的推理剧情，不展示内部思维链或虚构完成打勾。

流式输出不持续抢滚动位置；用户展开依据、编辑字段时不替换其输入或突然重排控件。建议变旧时标记“任务已更新，请重新生成建议”，保留用户未提交文字，不自动覆盖新业务状态。

## 7. 操作反馈与异常恢复

|场景|界面要求|
|---|---|
|首次加载|按实际布局显示骨架；无缓存时不显示假的任务内容|
|空列表|说明是无任务还是筛选后为空；提供报修或清除筛选入口|
|表单问题|错误贴近字段，提交后聚焦首个错误；保留已填内容|
|提交中|按钮立即进入执行中并防重复触发；可继续查看内容|
|已提交待回读|显示“已提交，正在更新结果”；不得提前切换成功阶段|
|接单/预约冲突|简短解释并刷新结果；不给另一个用户虚假的成功提示|
|网络中断|标记缓存时间并禁用业务写；未保存内容明确标“未保存”，恢复后由用户重试|
|响应丢失|使用原请求幂等键重试核对，不能因网络报错重新创建任务|
|模型失败|保留输入与人工表单；重试入口明确，不无限转圈|
|附件失败|失败卡片保留文件名与重试/移除动作，不伪装上传完成|
|没有权限/会话失效|清除敏感详情和账号缓存，提供重新登录/授权；不泄漏对象是否存在|

草稿保存复用现有update_draft命令：合并有效编辑、串行提交、按最新返回版本推进，显示保存中/已保存/未保存。未通过字段校验时仅保留当前编辑会话；未保存离开须提示，不承诺离线持久草稿。用户输入不默认存入跨账号共享localStorage。

普通可逆操作不层层要求二次确认；预约确认、改派、取消、验收用清楚的内容核对面板完成。收到服务端权限询问与业务核对时说明两者目的，避免重复展示没有对象信息的“确定吗”。

## 8. 视觉语言与基础参数

|元素|默认设计初值|用途|
|---|---|---|
|背景|#111A1B|整体安静、留白明确|
|内容面|#1A2628|主要表单、详情、浮层|
|主要文字|#E2EDEA|标题、关键字段|
|辅助文字|#A4B8B3|时间、来源、补充说明，仍须清晰可读|
|主色|#91D5BE|主按钮、选中项、关键交互|
|主色浅底|#223638|建议区、选中背景；不等同于操作成功|
|成功 / 待处理 / 错误|#91D5BE / #EBCB8B / #FFABA0|同时使用文字和图标，不只靠颜色|
|分隔线|#35494A|轻量组织；可交互控件需另核验边界可辨认|
|字体|系统中文无衬线；标题24–28，区块18–20，正文15–16，辅助13–14|不把主要业务信息压到小字号；数字/编码保持易读|
|间距|4/8/12/16/24/32|少量统一尺度；同类组件对齐|
|圆角|输入/按钮7，普通卡/主面板12|保持层级一致，不把每个元素都做成药丸|
|点击区域|常用按钮和图标命中区至少40×40，主要按钮高44|图标视觉尺寸可小于命中区|

图标使用一套线性风格，线宽与尺寸一致；常用动作图标带文字。颜色、字重、留白共同形成层级，不依赖彩色边框与重阴影堆叠。外部未接入在任务信息中以克制的中性标签呈现；本地确实失败时才使用错误色。

以上色值必须以实际前景/背景组合检查：普通文字对比目标至少4.5:1，焦点和关键控件边界目标至少3:1。这是项目验收目标，尚未逐项测定，不能因填入色值就声明无障碍达标。

## 9. 动效、键盘和原生质感

- 轻反馈约120–180ms，面板展开约180–240ms；作为初值在真实宿主测量。动效服务方向感，不拖慢确认。
- 新进度短暂强调，完成阶段平稳更新；等待、失败、取消不得播放庆祝效果。尊重减少动态效果设置。
- Tab顺序符合阅读顺序；焦点可见；弹层关闭后回到触发控件；不能仅靠悬停发现重要操作。
- Enter在多行报修文本里换行；不能意外提交验收或取消。Esc有未保存内容时先提示，不能静默丢弃。
- 支持复制设备编码/任务号、键盘选择候选、明确的附件焦点操作；拖放只能作为补充，必须有选择文件按钮。
- 长地点、长设备名和超长中文必须有换行/展开策略；摘要可截断，提交前核对内容、错误信息和主要动作不可被截断。
- 使用逻辑像素，验证高DPI与文字放大；Makepad所选版本的焦点、文件选择、辅助技术能力在G0登记实测结果，未验证的能力不假设已支持。

## 10. 交给设计和编码模型的交付要求

先按真实业务做6组关键画面：工作台与详情、报单草稿与歧义选择、预约确认与冲突、设备身份与依据、处理上传与失败、验收通过/退回。它们覆盖八个页面/面板，不要求为每个状态新建独立路由。

设计交回：页面结构、可点击正常/异常流程、视觉token与组件状态表、长文本/窄窗/放大效果、角色动作映射。编码交回：真实原生实现及操作证据；HTML/Figma图只能作为设计参考，不能算宿主实现。

优先形成一个完整任务的交互原型，再沿token扩展页面。不得为了页面看起来丰富增加没有业务来源的天气、统计、预测进度或设备实时数据。新组件如需改变接口，先补04契约和测试，不从模型建议里补造字段。

## 12. 修改与验证方式

更改布局/token先同步本文件、组件说明和关键画面；更改交互动作须同步01需求、04接口及对应T/U用例。执行verify_pack.py只证明交付文件与链接等结构正确，不证明UI好看、好用或满足对比要求。

置信度：角色与业务交互要求高；视觉方向为当前设计选择，需高保真画面确认效果；原生控件、键盘与窗口适配需实现后验证。当前未制作高保真稿，未完成用户可用性测试。
